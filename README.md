# ColdKeeper

Мониторинг температуры холодильного оборудования: электронный температурный журнал с выгрузкой, история измерений,
инциденты и уведомления в Telegram об устойчивых отклонениях.

MVP включает: веб-интерфейс (обзор, объекты и оборудование, карточка с графиком, датчики и привязки, журнал и
выгрузка CSV/XLSX, инциденты, получатели уведомлений), приём показаний UnitX по HTTP push, фоновый worker
(пропажа связи, доставка уведомлений), симулятор UnitX и демо-данные.

> Электронный журнал предназначен для производственного контроля. Правило ежедневного журнала и пороги — настройки
> ColdKeeper, а не обещание соответствия нормативным документам, сертификации или поверки.

## Требования

- [uv](https://docs.astral.sh/uv/) — Python и зависимости (Python 3.13 uv установит сам по `.python-version`);
- [Task](https://taskfile.dev/) — единая точка входа для команд;
- Node.js 22 и npm — frontend;
- Docker Desktop / Docker Engine с Compose v2 — PostgreSQL, тестовая БД и запуск всего стека.

Если репозиторий лежит внутри хранилища Obsidian, исключите `frontend/node_modules` в настройках Obsidian
(«Файлы и ссылки → Исключённые файлы»), иначе Obsidian будет индексировать десятки тысяч файлов.

## Быстрый старт в Docker (демо)

```bash
task up
```

```bash
task demo:docker
```

`task up` собирает образы, применяет миграции и запускает БД, API, worker и Caddy на http://localhost:8080.
`task demo:docker` создаёт демо-данные, загружает 7 суток истории через публичный ingest (около 4 минут)
и запускает живой симулятор.

Демо-логины и пароли генерируются при первом seed и хранятся только локально:

```bash
docker compose --profile demo run --rm --no-deps --entrypoint cat seed /app/.demo/credentials.json
```

- `demo-owner` — владелец кафе «Север» (демо): 2 помещения, 3 единицы оборудования, 4 точки;
- `demo-observer` — наблюдатель той же организации (просмотр и выгрузка);
- `demo-shop` — владелец второй организации «Магазин «Юг» (демо)» — для проверки изоляции.

Остановить: `task down` (данные БД сохраняются в томе `pgdata`).

## Локальная разработка (Windows и Linux)

```bash
task install
```

```bash
task db:up
```

```bash
task migrate
```

Затем в трёх терминалах: `task dev:api` (http://localhost:8000), `task dev:worker`, `task dev:web`
(http://localhost:5173; запросы `/api` проксируются на API — один origin, как за Caddy).

Настройки читаются из переменных окружения или `.env` (образец — `.env.example`; файл `.env` не коммитится).
Без `.env` используются значения для локальной разработки.

Демо локально:

```bash
task seed:demo
```

```bash
task sim:history
```

```bash
task sim
```

`seed-demo` идемпотентен: повторный запуск не создаёт дубли, сохраняет точку отсчёта истории и действующие ключи из
`.demo/devices.json` (запущенный симулятор продолжает работать, повторная загрузка истории не даёт конфликтов);
новый ключ выпускается, только если прежний утерян или отозван. Пароли — в `.demo/credentials.json`
(каталог `.demo/` в `.gitignore`).
При `COLDKEEPER_ENV=production` команда отказывается работать.

### Организации и пользователи

Публичной регистрации нет. Организации и пользователей создаёт команда ColdKeeper:

```bash
uv run --locked coldkeeper create-org "ООО Ромашка"
```

```bash
uv run --locked coldkeeper create-user --org "ООО Ромашка" --login ivanov --role owner --generate-password
```

Роли: `owner` (настройки, датчики, получатели, просмотр, выгрузка) и `observer` (просмотр и выгрузка). Пароль
можно передать через `COLDKEEPER_NEW_PASSWORD` или ввести в консоли; `set-password` меняет пароль.

## Архитектура

Модульный монолит; зависимости направлены внутрь, проверяются import-linter (`task lint`).

```
backend/
  domain/        правила без фреймворков: статусы и инциденты, журнал, датчики и назначения, ошибки
  application/   сценарии (ingest, мониторинг, журнал, датчики, инвентарь, вход, уведомления) и порты (Protocol)
  adapters/      PostgreSQL (SQLAlchemy async, миграции), UnitX, Telegram (aiogram), CSV/XLSX, scrypt, токены
  interfaces/    HTTP (FastAPI), worker, CLI
  composition.py единственное место сборки реализаций (явная DI через конструкторы, без контейнера)
  simulator/     отдельный клиент UnitX: не импортирует серверный код и ходит только через публичный ingest
frontend/        React + TypeScript + Vite, uPlot, собственные компоненты (без UI-кита)
```

- Домен и сценарии не импортируют FastAPI, SQLAlchemy, aiogram, httpx, openpyxl и настройки.
- Транзакция — Unit of Work (`application/ports.py` → `adapters/db/unit_of_work.py`): без явного `commit` всё
  откатывается. Репозитории фильтруют по организации в SQL-запросе.
- Тесты подменяют часы (`FakeClock`) и отправителя уведомлений, не меняя бизнес-код.

## Приём показаний UnitX

Контракт (наш, задаётся в URL HTTP push устройства):

```
POST /api/v1/ingest/unitx?token=<ключ устройства>[&rssi={rssi}]
{"id": "utx-ae4634", "ts": 1792711142, "t": 23.6, "ok": true}
```

- `id` — аппаратный ID; должен совпадать с ключом (иначе 403). `ts` — Unix-секунды, `t` — °C, `ok` — ответил ли
  зонд. `rh` (UnitX-D) необязателен; пустое значение — «нет данных». Лишние поля игнорируются.
- `ok=false` сохраняется как отказ датчика без температуры (никогда не как 0 °C). `ok=true` без `t`, NaN,
  бесконечность, строки вместо чисел — 422.
- Ответы: `204` — сохранено (только после commit) или идентичный повтор; `401` — неверный/отозванный ключ;
  `403` — чужой аппаратный ID; `409` — для этого времени уже сохранено другое значение (история не
  перезаписывается); `400` — не JSON; `413` — больше 4 КБ; `422` — некорректное измерение, время в будущем
  больше чем на 5 минут или старше 30 суток; `5xx` — временная ошибка (устройство повторит).
- По документации UnitX на 400/401/403/404/413 устройство прекращает повторы до смены адреса; реакция на 409/422
  не описана — проверить на устройстве.
- Показание, пришедшее, когда датчик не привязан к точке, сохраняется за датчиком («не назначен») и не попадает в
  журнал точки.
- Показания старше двух ожидаемых интервалов на момент приёма — «поздние»: сохраняются в историю и журнал, но не
  меняют текущий статус и не открывают инциденты. Правило одинаково для устройств и симулятора.

Ключ выдаётся при регистрации датчика или перевыпуске (раздел «Датчики»), показывается один раз; на сервере хранится
SHA-256. Ключ вырезается из логов uvicorn (`token=***`) и Caddy (`token=REDACTED`).

Пример запроса (подставьте ключ и ID зарегистрированного датчика):

```bash
curl -i -X POST "http://localhost:8000/api/v1/ingest/unitx?token=KEY" -H "Content-Type: application/json" -d "{\"id\":\"utx-ae4634\",\"ts\":$(date +%s),\"t\":4.2,\"ok\":true}"
```

PowerShell:

```powershell
$ts = [DateTimeOffset]::UtcNow.ToUnixTimeSeconds(); Invoke-RestMethod -Method Post -Uri "http://localhost:8000/api/v1/ingest/unitx?token=KEY" -ContentType "application/json" -Body "{`"id`":`"utx-ae4634`",`"ts`":$ts,`"t`":4.2,`"ok`":true}"
```

### Переход с симулятора на реальный UnitX (без изменения кода)

1. Уберите датчик точки из демо-программы (остановите `task sim` или запустите без него: `--only`) и отзовите ключ
   симулируемого датчика.
2. Зарегистрируйте реальный датчик: аппаратный ID, источник «Реальное устройство»; сохраните выданный ключ и URL.
3. Привяжите его к точке: привязка старого датчика закрывается в тот же момент. Старые измерения остаются за точкой
   с пометкой «симуляция»; новые получают пометку «датчик».
4. Для работы через интернет нужен подтверждённый защищённый канал от устройства (HTTPS прошивки или иной
   проверенный способ). HTTPS на Caddy не добавляет TLS самому устройству; до проверки подключайте датчик в
   доверенной сети.
5. В устройстве: Wi-Fi 2,4 ГГц, канал HTTP push, метод POST, URL с ключом, интервал 60 секунд
   (по умолчанию у UnitX — 5 минут; с ним таймаут «нет связи» надо увеличить).
6. Убедитесь, что в карточке датчика появились показания и точка в норме.

Другой производитель или протокол (например, MQTT) — новый входной адаптер, который строит тот же `Reading`;
сценарий приёма, журнал, тревоги, БД и интерфейс не меняются. Совместимость с реальным UnitX проверена только
программно (по документированному формату), не на устройстве.

## Симулятор и демо-сценарии

Сценарная модель на `random.Random(seed)` + `math` (без NumPy): термостат с гистерезисом даёт плавный цикл охлаждения,
шум ограничен и округлён до 0,1 °C, открытая дверь — быстрый кратковременный скачок, отказ компрессора — устойчивый
рост до восстановления, пропажа связи — точки не отправляются, отказ зонда — `ok=false` без температуры.
Генерация — чистая функция (`backend/simulator/generator.py`) без часов, ожидания и HTTP: одинаковые seed, начало,
шаг, длительность и сценарий дают одинаковый ряд (при версиях из `.python-version` и `uv.lock`). Это правдоподобный
демо-сигнал, а не физическая модель конкретного холодильника.

История и живой поток — один непрерывный ряд от `history_start` в `.demo/devices.json`, поэтому повторная загрузка
истории отправляет те же значения (идемпотентно), а будущие даты не создаются никогда.

| Датчик | Живой сценарий |
| --- | --- |
| `demo-fridge-1` | `door_spikes` — короткие скачки, тревога не подтверждается |
| `demo-combo-cool` | `sustained_excursion` — отказ компрессора 30 мин: тревога и восстановление |
| `demo-combo-freeze` | `probe_failure` — отказ зонда |
| `demo-chest-1` | `connection_loss` — 8 минут без связи |
| `demo-shop-1` | `normal` |

Демо-точки используют помеченный профиль коротких таймаутов (отклонение 3 мин, восстановление 2 мин, нет связи
3 мин). Разовые команды: `task sim:scenarios`, `task sim -- --scenario demo-shop-1=sustained_excursion`,
`task sim -- --only demo-fridge-1`, просмотр ряда без отправки:
`uv run --locked coldkeeper-sim preview --scenario sustained_excursion --minutes 60`.

Тревога по команде для живой демонстрации: `task demo:alarm` (на VPS — `sh deploy/demo-alarm.sh`) перезапускает
симулятор со сценарием `door_left_open` на `demo-fridge-1`: тревога примерно через 5 минут после команды,
восстановление примерно через 13–14 минут. Показания идут через публичный ingest, поэтому инцидент, событие
уведомления и сообщение в Telegram настоящие. Вернуть обычную программу: `task demo:alarm:stop`
(`sh deploy/demo-alarm.sh stop`).

## Мониторинг и уведомления

- На точке задаются пороги, длительность отклонения (по умолчанию 5 мин), длительность подтверждённой нормы для
  закрытия (2 мин), ожидаемый интервал (60 с) и таймаут связи (5 мин, не меньше двух интервалов).
- Нормальное значение сбрасывает ожидание тревоги; отказ зонда и пауза больше 2,5 интервалов прерывают
  подтверждение; отсутствие данных не продлевает и не закрывает тревогу.
- Инциденты хранятся в БД, не больше одного открытого инцидента каждого типа на точку; перезапуск worker не
  создаёт дублей. Уведомления — при открытии и восстановлении, не на каждое измерение.
- События уведомлений сохраняются всегда; без получателей или без бота интерфейс честно показывает
  «не отправлено». Доставка — очередь в PostgreSQL с ограниченными повторами и видимой ошибкой.

Telegram: создайте бота у @BotFather, задайте `COLDKEEPER_TELEGRAM_BOT_TOKEN` и `COLDKEEPER_TELEGRAM_BOT_USERNAME`,
перезапустите worker. Запускайте **один** экземпляр worker (Telegram допускает одного получателя обновлений на бота).
В разделе «Уведомления» владелец получает одноразовый код (15 минут); получатель открывает ссылку
`t.me/<бот>?start=<код>` или отправляет боту `/start <код>`. Без токена работает dry-run: сообщения не отправляются,
это видно в интерфейсе.

На демонстрационном стенде с `COLDKEEPER_PUBLIC_DEMO=true` участник открывает личный чат с ботом и нажимает
«Старт». Бот подписывает этот чат на новые тревоги и сообщения о восстановлении кафе «Север» (демо).
Повторный `/start` возобновляет подписку, если она была на паузе.

## Журнал и выгрузка

- Два представления: исходные измерения и ежедневный журнал (строка «дата × точка», все дни периода, включая дни
  без данных).
- Контрольное значение суток — первое корректное измерение в окне после контрольного времени объекта (по умолчанию
  10:00 местного времени, окно 30 минут); иначе «нет данных». Дополнительно — суточные min/max и покрытие суток.
  Пропуски не интерполируются, значения не подставляются.
- Сутки считаются в часовом поясе объекта (IANA, по умолчанию `Asia/Vladivostok`).
- Печатная форма в Word (DOCX) по рекомендуемому образцу приложения N 2 к СанПиН 2.3/2.4.4282-26 («Журнал учета
  температурного режима холодильного оборудования»): на каждый объект и месяц — альбомный лист A4, строка на единицу
  оборудования (у оборудования с несколькими секциями — на секцию), столбец на день месяца, в ячейке — контрольное
  значение суток; «—» — нет данных, «о.д.» — ошибка датчика. Внизу — строка для подписи ответственного лица.
  П. 35 СанПиН допускает ежедневную регистрацию на бумажном и (или) электронном носителе; образец рекомендуемый,
  оформление (шрифты, поля) им не регламентировано.
- CSV для русского Excel: `;`, UTF-8 с BOM, десятичная запятая, даты `ДД.ММ.ГГГГ`; XLSX с типизированными
  ячейками. Текстовые ячейки защищены от formula injection. Если в периоде есть симуляция, имя файла получает
  суффикс `_demo`, а в строках указан источник «симуляция». Печать — из браузера.

## Безопасность

- Сессии хранятся в PostgreSQL; cookie `HttpOnly`, `SameSite=Lax`, `Secure` в production; выход отзывает сессию.
- Пароли — `hashlib.scrypt` (параметры OWASP с умеренной памятью), лимит неудачных входов: 5 попыток → пауза 15 минут.
- Изменяющие запросы требуют CSRF-токен сессии (`X-CSRF-Token`) и проверяют `Origin`.
- Данные организаций изолированы на сервере: чужой ID → 404.
- За Caddy uvicorn доверяет заголовкам `X-Forwarded-*` только от адреса proxy; порт API наружу не публикуется.

## Размещение на VPS (инструкция; деплой не выполнялся)

1. Домен: свой или бесплатный поддомен DuckDNS (подходит для демо; без SLA — для клиентов лучше свой). A-запись
   на IP VPS; порты 80 и 443 открыты (80 нужен для выпуска сертификата).
2. На VPS установите Docker, скопируйте репозиторий, создайте `.env` по `.env.example`: `COLDKEEPER_ENV=production`,
   `SITE_ADDRESS=<домен>`, `COLDKEEPER_PUBLIC_URL=https://<домен>`,
   `COLDKEEPER_ALLOWED_ORIGINS=["https://<домен>"]`, длинный `POSTGRES_PASSWORD`, при необходимости токен бота.
3. Запуск (миграции применяются автоматически сервисом `migrate` перед API и worker):
   `docker compose -f docker-compose.yml -f deploy/docker-compose.prod.yml up -d --build`.
4. Создайте организацию и владельца: `docker compose exec api coldkeeper create-org "…"` и `create-user …`.
5. Данные БД — в томе `pgdata`, сертификаты — в `caddy-data`. Резервная копия:
   `docker compose exec -T db pg_dump -U coldkeeper coldkeeper > backup.sql`; храните копии вне сервера и
   проверяйте восстановление.
6. Обновление: `git pull`, затем та же команда `up -d --build`.

### VPS, где 80 и 443 уже заняты другим Caddy

Второй сервис не может занять те же порты, поэтому сертификат для домена ColdKeeper выпускает уже работающий Caddy,
а прокси ColdKeeper слушает только локальный порт (`deploy/docker-compose.behind-proxy.yml`).

1. A-запись (или поддомен DuckDNS) на IP VPS, например `coldkeeper.example.ru`.
2. В `.env` на VPS, кроме значений из шага 2 выше (`SITE_ADDRESS` не нужен):
   `COMPOSE_FILE=docker-compose.yml:deploy/docker-compose.behind-proxy.yml` и свободный порт `HTTP_PORT=8081`.
   С `COMPOSE_FILE` любая команда `docker compose` берёт оба файла, и порт 8080 случайно не откроется наружу.
3. В Caddyfile существующего Caddy добавьте сайт и перезагрузите его (`caddy reload` или перезапуск контейнера):

   ```caddyfile
   coldkeeper.example.ru {
   	reverse_proxy 127.0.0.1:8081
   }
   ```

   Если существующий Caddy сам работает в Docker, `127.0.0.1` — это его контейнер: задайте в `.env`
   `PROXY_BIND=172.17.0.1` (адрес моста Docker на хосте) и укажите `reverse_proxy 172.17.0.1:8081`.
   Если для сайтов включён `log`, добавьте тот же фильтр `replace token REDACTED`, что в `deploy/caddy/Caddyfile`:
   ключи устройств передаются в адресе запроса.
4. Запуск: `docker compose up -d --build`. Прокси ColdKeeper доверяет `X-Forwarded-For` и `X-Forwarded-Proto` только
   с частных адресов (`CADDY_TRUSTED_PROXIES=private_ranges`), поэтому API видит настоящий IP клиента и схему https.
5. Проверьте, что подсеть `172.28.0.0/24` (сеть `internal` в `docker-compose.yml`) не занята другим проектом
   (`docker network inspect`), и что `docker compose version` не ниже 2.24 (нужны `!reset` и `!override`).

Демо-стенд на VPS (данные симулятора, `seed-demo` при `COLDKEEPER_ENV=production` запрещён намеренно, поэтому
разовый запуск явно переопределяет среду):

```bash
docker compose --profile demo run --rm -e COLDKEEPER_ENV=development seed
docker compose --profile demo run --rm simulator coldkeeper-sim history --url http://proxy
docker compose --profile demo up -d simulator
docker compose --profile demo run --rm --no-deps --entrypoint cat seed /app/.demo/credentials.json
```

Telegram: токен от @BotFather в `COLDKEEPER_TELEGRAM_BOT_TOKEN`, имя бота без `@` в
`COLDKEEPER_TELEGRAM_BOT_USERNAME`. Long polling допускает одного клиента на токен: не запускайте worker с тем же
токеном локально, пока работает VPS.

## Допущения и открытые вопросы

- Первая интеграция — HTTP push; MQTT отложен.
- Поддержка TLS прошивкой UnitX не подтверждена; реакция устройства на 409/422 и точность его часов — проверить на
  железе.
- Автоматического восстановления архива устройства после обрыва связи нет: пробелы честно видны, задержанные
  показания принимаются как история.
- Правила журнала и пороги — настройки MVP, а не нормативное соответствие.
